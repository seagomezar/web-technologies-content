From a conversation with
@ngparker
While
readOnlyHint
is a very useful indicator for agents, enforcing strict HITL rules based on read vs. write actions can be a bit reductive. It would be great to understand whether an action can be easily reversed without consequences for the end user. Depending on user preferences, agents could decide to skip confirmations for these reversible actions.
For example, drafting an email is not a read only action, but it is also not something that commonly needs to be confirmed with the user. Sending the email, however, is not reversible and should definitely be confirmed.
This could also be called
consequentialHint
if we wanted to reverse the boolean order, though I prefer "reversible" to be consistent with readOnly.
MCP's
destructiveHint
comes close but doesn't feel like it quite hits the same note - there are many possible non-deletion actions that users may take that warrant user confirmation.
See also
#53

I talked with
@johannhof
more after today's call, and raised the issue that if the hint we land on is supposed to be a strong signal for the agent harness to react to / loop in the user, it shouldn't be on "by default". Probably most tools are not destructive or consequential, so we can't rely on 90% of tools supplying
destructiveHint: false
if it defaults to true, or supplying
reversibleHint: true
if it defaults to false.
So to keep this a meaningful signal that doesn't get diluted, probably tools should be reversible or "non-destructive" by default, and we can pick whatever name makes the most sense with an "off-by-default" model.

To move the bikeshedding along,
I would make a soft stance that I now prefer having it to be consequentialHint
(default = false) alongside good documentation, following the discussion during today's meeting. This would be based on the following reasons.
I looked at
destructiveHints
existing use cases by MCP tools. In most situations, they are indeed restricted to "delete" or "remove" kind of tools, but there are quite a few instances where it's adopted loosely as "consequential or important". The example below were all proposed by the same anthropic employee, but they are adopted by different project maintainers:

makenotion/notion-mcp-server#169
- creating and cloning were tagged as
destructive
feat: Add tool annotations to MongoDB tools for improved LLM understanding
googleapis/mcp-toolbox#2219
- insert operations were tagged as
destructive
feat: Add tool annotations for improved LLM tool understanding
razorpay/razorpay-mcp-server#73
- create, refund tools were tagged as
destructive
This indicates the acceptance of a broader term than
destructive
which doesn't exist in the MCP spec right now.
For most parts, I can see many WebMCP tools wanting something to indicate "important or consequential" actions, and yet "reversible=false" might not be
exactly

"purchase items in my shopping cart" (e.g. technically you could refund in 24 hours...)

Having consequential hints be applicable can help mitigate developers from wanting to use

I agree with you both, but want to note that the preferred default value really depends on what you're trying to achieve with the hint. Right now readOnly defaults to "false" because that's the safest assumption for its purpose - we should only consider a tool read-only if the author explicitly confirms it, e.g. if you wanted to expose your agent only to read-only tools it would be bad if that accidentally included non-read only tools.
Are we confident that within the usage we envision for this hint, it's safe to assume tools are "not consequential" by default, e.g. including in cases where the developer simply forgot to tag them? (I'm not suggesting it's not, just want to make sure we're picking correctly here).
